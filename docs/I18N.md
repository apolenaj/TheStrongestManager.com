## Intent

Prepare the platform for multilingual expansion:

| Locale | Status | Direction |
| --- | --- | --- |
| **English** (`en`) | **Active** | LTR |
| Czech (`cs`) | Planned shell | LTR |
| German (`de`) | Planned shell | LTR |
| Spanish (`es`) | Planned shell | LTR |
| Arabic (`ar`) | Planned shell | **RTL** |

## Architecture

```text
UI / RSC  →  t(key) / useI18n().t
                │
                ▼
        src/domain/i18n/
          locales · catalogs · terminology glossary
                │
                ▼
        English catalog (source of truth today)
        Planned catalogs empty until authored + reviewed
```

| Rule | Detail |
| --- | --- |
| No hard-coded UI copy | Migrated surfaces use message keys (`a11y.*`, `common.*`, `i18n.*`, …) |
| English fallback | Missing keys in planned locales resolve to English — never invent copy |
| Terminology review | RPE, RIR, 1RM, lift/method names stay English until `reviewedTranslations` is set |
| Preference cookie | `tsm_locale` reserved; planned ids fall back to active English at runtime |

## Terminology

`FITNESS_TERMINOLOGY` in `src/domain/i18n/terminology.ts`:

- **Do not automatically translate** technical fitness terms.
- Human review required before any locale-specific rendering.
- Unreviewed → always return `canonicalEn`.

## Adoption path

1. Add keys to `EN_MESSAGES`.
2. Call `t(key)` (server) or `useI18n().t(key)` (client).
3. When shipping a locale: fill its catalog + review terminology entries.
4. Flip locale `status` from `planned` → `active` only after review.

Existing pages still contain English literals; new and migrated UI must use catalogs. The admin console and skip-to-content link are the reference pattern.
